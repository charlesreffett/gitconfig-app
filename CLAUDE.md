## Architecture

The project is a desktop GUI for visually editing `.gitconfig` files. It has a strict three-layer structure:

### Layer 1 — `internal/config/`
Pure Go, no UI dependencies. Handles reading and writing the INI-style gitconfig format.
- `types.go` — `Config`, `Section`, `Entry` structs. `Entry.Key == ""` means a comment/blank line stored in `RawLine` for lossless round-trips.
- `parser.go` — line-by-line scanner; builds a `Config` from a file path.
- `writer.go` — atomically writes a `Config` back via temp-file + `os.Rename`. Also provides `SetEntry` and `DeleteEntry` helpers used by the UI layer.

### Layer 2 — `internal/schema/`
Pure Go, no UI dependencies. Defines the known structure of every git config section type.
- `types.go` — `SectionSchema` and `Field` structs. `FieldType` controls which widget renders: `FieldText`, `FieldToggle`, `FieldDropdown`, `FieldMultiline`.
- `sections.go` — the `All` slice of every known section schema (user, core, remote, branch, etc.).
- `registry.go` — case-insensitive `Lookup(name)` map built from `All`. Also provides `CommonFields`, `UncommonFields`, `FieldByKey`, `ConditionTypes`.

### Layer 3 — `app.go` + `main.go` + `frontend/`
Built with **Wails v2** (Go backend, Vue 3 frontend running in a native OS webview — no Electron, no localhost server).

**Go side (`app.go`)**: The `App` struct exposes bound methods called directly from Vue via Wails' JS bridge. It converts between `config.Section[]` ↔ `BlockDTO[]` using `sectionsToBlocks` / `blocksToSections`. DTOs are defined here and auto-typed in `frontend/wailsjs/go/main/App.d.ts` (regenerated by `wails dev/build`).

**Frontend (`frontend/src/`)**: Vue 3 + TypeScript + Tailwind CSS v4 + Reka UI primitives.
- `stores/app.ts` — Pinia store; owns all runtime state (blocks, schema, theme, status). Calls Go via `wailsjs/go/main/App`.
- `types.ts` — `Block` (client-side, has `superseded` per entry) and `BlockDTO` (wire format). `dtoToBlock` / `blockToDTO` convert between them.
- `components/blocks/` — one Vue component per block type: `SectionBlock`, `FileBlock`, `ConditionalBlock`, `CustomBlock`.
- `components/layout/` — `ConfigCanvas` (scrollable block list with `vue-draggable-plus` for reordering), `LibraryPanel` (click to add blocks).

The UI represents a gitconfig as a tree of typed **blocks**:
- `SectionBlock` — known sections (`[user]`, `[core]`, etc.) with schema-typed field rows
- `FileBlock` — an `[include]` or `[includeIf]` target file, shows child section blocks; edits to them are written back to the included file on save
- `ConditionalBlock` — one or more `[includeIf "condition:value"]` entries, wraps a `FileBlock`
- `CustomBlock` — unknown sections, free key=value pairs

The app shows two canvases side by side: **Global** (`~/.gitconfig`, loaded on startup) and **Project** (`.git/config`, loaded via folder picker). When both are loaded, `supersededKeys` (a computed Pinia getter) marks global keys overridden by the project config.

## Key Design Decisions

**Lossless round-trips**: Comments and blank lines are stored as `Entry{Key: "", RawLine: "..."}` and written back verbatim. Editing a section does not destroy surrounding comments.

**Atomic writes**: `config.Write` always writes to a temp file then `os.Rename`s it over the target. Never write directly to the real path.

**ConditionalBlock serialisation**: Multiple condition rows on one block expand into multiple `[includeIf]` sections that all point to the same `path` value. On load, consecutive `[includeIf]` sections with the same path are merged back into a single block.

**Schema-driven UI**: The `internal/schema` package is the single source of truth for what fields exist, their types, and their valid values. The UI never hard-codes field names.
